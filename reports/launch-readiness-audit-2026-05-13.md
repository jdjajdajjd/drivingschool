# vroom launch readiness audit — 2026-05-13

Аудит сделан по текущему локальному репозиторию и живому `https://vroom.today`. Код не менялся.

## Короткий вердикт

Проект уже выглядит как работающий прототип с сильным личным кабинетом ученика и заметно продвинутой операционной частью для школы, но до полноценного платного запуска еще не дошел.

Мой честный статус: **для публичного демо и показа — можно**, **для продажи школе как рабочий продукт на реальные деньги и реальные персональные данные — рано**.

Главная причина не в одном кривом экране. Главная причина в том, что под интерфейсом еще много временной архитектуры: клиентская авторизация, localStorage/compatibility-слой, устаревшие проверки, незакрытая типизация, слабые production-gates и неполная операционная логика вокруг платежей, сотрудников, уведомлений и онбординга школы.

Оценка готовности:

- Визуальная витрина и ученический сценарий: **70-80%**
- Рабочий кабинет школы как ежедневный инструмент: **55-65%**
- Безопасность и роли: **25-35%**
- Данные и мультиарендность: **45-55%**
- CI/CD и контроль качества: **35-45%**
- Готовность продавать B2B-клиенту: **примерно 50-60%**

## Стоп-факторы перед продажей

### 1. TypeScript сейчас красный

Команда:

```bash
npm run typecheck
```

Падает на доменных типах и UI-импортах. Примеры:

- `src/components/ui/HugeIcon.tsx`: `@hugeicons/react` не экспортирует `IconSvgObject`.
- `src/pages/admin/people/PeoplePage.tsx`: неполная обработка новых `TrainingStage`.
- `src/pages/student/studentUtils.ts`: неполная обработка новых `TrainingStage`.
- `src/services/bookingService.ts`, `src/services/seed.ts`, `src/services/supabaseAdminService.ts`, `src/services/studentService.ts`: рассинхрон по `StudentProgress.confirmedHours`.
- `src/services/studentProfile.ts`: неполная карта документов.

Это не “просто TS ворчит”. Это означает, что доменная модель уже изменилась, а интерфейсы, seed, админ-экраны и сервисы не приведены к одному контракту. Для продукта, где директор смотрит деньги, занятия, долги и статусы учеников, такой рассинхрон опасен.

Что нужно сделать:

- Привести `TrainingStage`, документы, прогресс ученика и статистику к одному источнику правды.
- Запретить merge/deploy, если `npm run typecheck` падает.
- После фикса типов прогнать реальные сценарии: ученик, школа, сотрудник, владелец.

### 2. Smoke-тесты устарели и сейчас не защищают продукт

Команда:

```bash
npm run smoke:vroom
```

Падает, потому что тест все еще ждет старую публичную запись и тексты вроде “Главная / Запись / О нас / Контакты”, хотя продуктовая логика уже изменилась: запись должна быть внутри кабинета ученика.

Это плохой знак не потому, что тест “не тот”. Это значит, что автоматическая проверка живого сайта оторвалась от реального продукта. Сейчас она не ловит то, что важно, и ругается на то, что уже не является целью.

Что нужно сделать:

- Переписать smoke под текущий продукт:
  - главная не содержит старые/грязные названия;
  - публичная страница школы ведет во вход/регистрацию, а не в гостевую запись;
  - ученик может войти/открыть кабинет;
  - школа может войти и увидеть день/расписание/учеников;
  - нет белого экрана при lazy-route;
  - нет mojibake-текстов;
  - нет горизонтального скролла на mobile.
- Включить smoke в CI до деплоя.

### 3. Авторизация школы и владельца пока не production-grade

В `src/services/accessControl.ts` была клиентская проверка логина/пароля и fallback-credentials, включая статические значения для доступа школы и владельца.

Доступ хранится через `sessionStorage`. Пароль для admin RPC тоже кладется в sessionStorage.

Это нельзя продавать как полноценный кабинет школы. Любой production B2B-продукт с учениками, телефонами, оплатами, документами и сотрудниками должен иметь нормальную серверную авторизацию:

- Supabase Auth или отдельный backend auth.
- Роли: владелец, директор, администратор, инструктор, возможно бухгалтер.
- Привязка пользователя к конкретной школе.
- Нормальные сессии, reset password, revoke sessions.
- Audit log с реальным user id, а не “Менеджер школы”.
- Запрет админских операций без проверенной роли на сервере.

### 4. Supabase RPC открыт через `anon/authenticated` и защищен общим staff password

В `supabase/DRIVEDESK_FULL_SETUP.sql` много `security definer` функций и grants на `anon, authenticated`, включая:

- `public_admin_list_students`
- `public_admin_list_bookings`
- `public_admin_update_student`
- `public_create_slot`
- `public_delete_slot`
- `public_update_school_settings`
- `public_upsert_branch`
- `public_upsert_instructor`
- `public_cancel_booking`
- `public_complete_booking`
- `public_reschedule_booking`

Часть функций проверяет `p_staff_password`. Это лучше, чем вообще без проверки, но для продажи все равно слабая модель:

- общий пароль школы становится ключом от всех административных действий;
- нет персональной ответственности сотрудника;
- трудно разделить права;
- сложно безопасно уволить сотрудника;
- если пароль утек из браузера, ущерб широкий;
- потенциально тяжело пройти нормальный security review у клиента.

Нужно переводить на server-side RBAC/RLS: `auth.uid()` → school membership → role → permission.

### 5. Данные школы еще живут в transitional compatibility layer

README прямо фиксирует текущее состояние:

- Supabase data syncs into in-memory compatibility layer.
- Admin auth is temporary access gate.
- Admin screens render through in-memory bridge.
- Next priorities: move admin reads fully to Supabase, replace temporary staff passwords with real Supabase Auth roles.

Плюс в `src/services/storage.ts` и `src/services/adminStorage.ts` активно используется localStorage/data namespace. Это нормально для демо и быстрой разработки, но не для продажи, где:

- директор ожидает, что данные не исчезнут при другом браузере;
- сотрудник работает с другого устройства;
- у школы несколько людей одновременно меняют расписание;
- нужно защищать персональные данные;
- нужно видеть историю действий;
- нужна консистентность расписания и оплат.

Что нужно сделать:

- Все school-admin reads/writes перевести на Supabase.
- localStorage оставить только для UI-предпочтений, не бизнес-данных.
- Ввести server-side conflict checks для времени инструктора, занятия, оплаты, статуса.

### 6. На production есть текстовые/кодировочные артефакты

В `src/App.tsx` в fallback loader сейчас есть mojibake:

```tsx
label={isAdmin ? 'Р—Р°РіСЂСѓР·РєР° РєР°Р±РёРЅРµС‚Р°' : 'Р—Р°РіСЂСѓР·РєР°'}
```

Это может проявиться именно в моменты медленной загрузки, то есть в самый заметный момент для пользователя: он переключил раздел, ждет, и видит мусорный текст.

В `scripts/smoke-vroom.mjs` тоже expected strings сохранены mojibake-строками. Это ломает доверие к текстовой чистоте проекта.

Что нужно сделать:

- Прогнать весь `src` и `scripts` на mojibake.
- Добавить тест/линт: в UI-текстах не допускаются `Р—`, `Рђ`, `Рљ`, `Рџ`, старые бренды и технические слова.

### 7. Гостевой маршрут записи все еще существует

В `src/App.tsx`:

- `/school/:slug/book` редиректит на login — это нормально.
- `/student/book` все еще открывает `BookingFlowPage`.
- `/booking/:bookingId` тоже доступен.

Если продуктовая позиция такая: “запись только внутри личного кабинета ученика”, то прямой `/student/book` надо либо убрать, либо сделать защищенным/встроенным маршрутом внутри кабинета.

Риск: пользователь или поисковик может открыть старую гостевую механику, а мы снова получим расхождение “как должно быть” и “что реально доступно”.

### 8. Живой кабинет школы может показывать generic school context

На live-проверке с принудительной session access кабинет школы показывал “Новая автошкола” вместо “Автошкола «Вираж»”. Это похоже на проблему namespace/bootstrap/workspace данных.

Для продажи это критично:

- клиент должен видеть свое название стабильно;
- нельзя, чтобы после входа появлялась “Новая автошкола”;
- onboarding новой школы должен создавать полный tenant record, а не полупустую заглушку.

Нужно отдельно проверить путь:

1. Создать школу.
2. Задать название, филиалы, инструкторов, категории, правила.
3. Выйти/зайти с другого браузера.
4. Убедиться, что та же школа и те же данные видны.

## Продуктовые пробелы

### 1. Онбординг школы не собран в безопасный launch flow

Сейчас есть элементы: супер-вход, создание школы, настройки, филиалы, инструкторы, категории. Но для продажи нужен не набор экранов, а понятный путь подключения.

Нужен мастер запуска школы:

1. Данные школы: название, телефон, адрес, публичная ссылка.
2. Филиалы.
3. Категории прав.
4. Инструкторы.
5. Машины.
6. Правила записи.
7. Первое расписание.
8. Тестовый ученик.
9. Проверка ссылки ученика.
10. “Школа готова принимать учеников”.

Директор не должен гадать, что еще не заполнено.

### 2. Нет зрелой модели сотрудников

Для реальной школы одного “кабинета школы” мало. Нужны:

- владелец/директор;
- администратор;
- инструктор;
- бухгалтер/кассир, если школа разделяет деньги;
- возможно менеджер филиала.

Каждая роль должна видеть и делать только свое:

- инструктор не должен видеть все оплаты школы;
- администратор может менять расписание, но не обязательно настройки тарифа;
- бухгалтер может принимать оплаты, но не удалять инструктора;
- владелец видит все.

Сейчас интерфейс уже содержит `Users`, но production auth/roles еще не доведены.

### 3. Платежи сейчас больше похожи на учет, чем на денежный модуль

В админке есть оплаты, долги, суммы, частичные оплаты. Но для запуска как продукта нужно определить уровень:

Минимум для MVP:

- вручную принять оплату;
- указать способ;
- видеть долг;
- видеть историю по ученику;
- нельзя случайно внести отрицательные/битые суммы;
- audit log;
- экспорт в CSV/XLSX.

Нормальный платный продукт:

- счета/квитанции;
- возвраты;
- рассрочка/пакеты занятий;
- разные цены по категориям;
- кто принял оплату;
- дата фактического платежа и дата внесения в систему;
- фильтры по периоду/филиалу/ответственному;
- выгрузка для бухгалтера.

Сейчас это нужно довести до четкого MVP-уровня и не обещать больше, чем реально работает.

### 4. Уведомления пока не являются работающим продуктовым контуром

В коде есть модули SMS/Telegram/напоминания, а в кабинете ученика текст “Напоминания пока не подключены”.

Для реального запуска нужно решить:

- либо честно убрать/спрятать уведомления как future module;
- либо подключить хотя бы один канал end-to-end.

Минимальный рабочий вариант:

- уведомление школе о новой записи/отмене;
- напоминание ученику перед занятием;
- уведомление инструктору;
- лог отправки;
- статус “доставлено/ошибка” хотя бы на базовом уровне.

Без этого директору все равно придется держать ручные переписки.

### 5. Конфликты расписания должны быть серверными

В продукте “расписание и запись” главное — не красивая таблица, а невозможность записать двух людей в одно и то же время к одному инструктору/машине.

Нужно убедиться, что на уровне базы есть:

- уникальность активной записи на конкретное время/инструктора;
- защита от гонки двух клиентов;
- запрет удаления занятого времени без обработки записи;
- история переноса/отмены;
- проверка лимитов ученика.

Часть логики есть в сервисах, но для продажи она должна быть на сервере/в базе, а не только в браузере.

### 6. Инструкторский кабинет выглядит как отдельный важный продукт, но его надо добить

Маршрут `/instructor/:token` есть. Для реальной школы это ценно, но нужно проверить:

- token нельзя подобрать;
- инструктор видит только себя;
- отметка “проведено/отменено” пишет в Supabase;
- комментарий сохраняется;
- директор видит изменения сразу;
- есть мобильный сценарий, потому что инструктор почти всегда с телефона.

Если это не доведено, лучше позиционировать как beta, а не как готовую часть.

### 7. Юридические документы нужно довести под реальную обработку данных

На сайте есть `/terms` и `/privacy`, но перед продажей нужно юридически проверить:

- кто оператор персональных данных;
- какие данные собираются: ФИО, телефон, email, обучение, документы, оплаты;
- на каком основании;
- кто имеет доступ;
- сроки хранения;
- передача автошколе/подрядчикам;
- удаление/изменение данных;
- согласие на обработку.

По актуальному тексту 152-ФЗ согласие на обработку персональных данных должно быть свободным и информированным; Роскомнадзор также публикует требования и разъяснения по уведомлению об обработке персональных данных. Это не заменяет юриста, но для запуска это нельзя оставлять как “потом”.

Источники для юридической проверки:

- https://www.consultant.ru/document/cons_doc_LAW_61801/6c94959bc017ac80140621762d2ac59f6006b08c/
- https://75.rkn.gov.ru/directions/p7166/

## UX и визуальная целостность

### Что уже хорошо

- Личный кабинет ученика выглядит как главный визуальный ориентир проекта.
- Основной стиль ученика уже отличается от типичного дешевого SaaS.
- В админской части появилась понятная логика “операционный пульт”, а не маркетинговая витрина.
- На live-проверке критичного горизонтального overflow на проверенных маршрутах не найдено.
- Основные маршруты отвечают 200 и без явных console/page errors.

### Что еще мешает ощущению дорогого продукта

1. **Разные визуальные эпохи в коде.**  
   В `src/pages/admin` есть новый набор страниц (`Today.tsx`, `Schedule.tsx`, `Students.tsx` и т.д.) и старые папки (`today/TodayPage.tsx`, `schedule/SchedulePage.tsx`, `people/PeoplePage.tsx`, `bookings/BookingsPage.tsx`, `money/MoneyPage.tsx`, `school/SchoolPage.tsx`). Это создает риск, что где-то всплывет старый стиль, старые термины или старые компоненты.

2. **Не все формы используют единый визуальный язык.**  
   В админке есть формы с `v-admin-input`, но также встречаются локальные классы `rounded-xl border-gray-200 bg-gray-50`, старые формы и неодинаковые placeholder/label patterns. Для директора это ощущается как “собрано из разных мест”.

3. **Есть маленькие кликабельные элементы.**  
   На `student-login` и `/student` ссылки “условия сервиса” и “политику конфиденциальности” имеют высоту около 17px. Для мобильного интерфейса это мелко.

4. **Повторы бренда еще стоит добить.**  
   На главной текстово встречается несколько `vroom`, на публичной странице школы есть `vroom.today`. После истории с логотипами нужно оставить бренд там, где он нужен, и не превращать каждый экран в повтор имени.

5. **Тексты должны стать словарем продукта.**  
   Нужно запретить слова уровня “админка”, “слоты”, старые бренды, mojibake, “demo” в пользовательском UI. В админской части лучше говорить:
   - “кабинет школы”
   - “расписание”
   - “свободное время”
   - “занятия”
   - “ученики”
   - “оплаты”
   - “сотрудники”

6. **Нужно провести финальный mobile-first QA.**  
   Особенно:
   - боковое меню кабинета школы;
   - таблицы оплат/учеников;
   - расписание;
   - модалки создания;
   - long names: длинное ФИО, длинный филиал, длинная марка машины;
   - маленькие экраны 360px.

## Техническое качество

### Build проходит, но это слабый критерий

`npm run build` проходит, но:

- `typecheck` падает;
- `smoke` падает;
- `audit` падает;
- CI запускает только build.

Это значит, что production может обновиться при поломанной типизации и устаревших сценарных проверках.

### Уязвимость в dependency tree

`npm audit --audit-level=moderate` показывает 2 moderate vulnerabilities через `esbuild <=0.24.2`, цепочка идет через Vite. `npm audit fix --force` предлагает major upgrade до Vite 8.

Нужно не просто нажать force, а сделать аккуратный upgrade-plan:

1. Поднять Vite/plugin-react до безопасной совместимой версии.
2. Проверить `vite.config.ts`, build, preview.
3. Прогнать Playwright smoke.
4. Деплоить только после проверки.

### Бандл уже крупный

Build warning: основной JS chunk больше 500 kB. Это не блокер, но для мобильных пользователей и слабых устройств важно.

Нужно:

- проверить code splitting по большим admin sections;
- не грузить superadmin/admin/student-heavy код на главной;
- анализировать bundle visualizer;
- лениво грузить тяжелые библиотеки и иконки.

### CI/CD недостаточный

`.github/workflows/deploy.yml` делает:

1. npm ci
2. npm run build
3. deploy Cloudflare Pages

Нужно добавить до deploy:

- `npm run typecheck`
- `npm run smoke:vroom` для preview или production smoke после preview deploy
- `npm audit --audit-level=moderate` или отдельный controlled security check
- lint/format, если добавим
- Playwright mobile/desktop smoke
- проверку forbidden UI strings

## Безопасность

### Главные риски

1. Клиентские fallback-логины и пароли.
2. Хранение студенческих credentials/password-like values в localStorage.
3. Admin RPC доступны через anon/authenticated grants и shared password.
4. Нет полноценного RBAC.
5. Нет надежного server-side audit identity.
6. Нет security headers полного уровня.
7. Нет видимой политики backup/restore и retention.

### Заголовки production

На `https://vroom.today` есть:

- `x-content-type-options: nosniff`
- `referrer-policy: strict-origin-when-cross-origin`

Не видно:

- `Content-Security-Policy`
- `Strict-Transport-Security`
- `Permissions-Policy`
- `X-Frame-Options` или `frame-ancestors` через CSP

Для продукта с персональными данными это нужно закрыть.

### Supabase config

В `src/lib/supabase.ts` hardcoded Supabase URL и anon key. Anon key сам по себе не секрет, но hardcoded production fallback опасен организационно:

- локальная сборка может случайно работать с production;
- другой агент/чат может не понять, куда пишет;
- env config перестает быть явным;
- труднее разделять dev/staging/prod.

Нужно:

- убрать silent fallback на production;
- сделать явные env для dev/staging/prod;
- если env нет — показывать безопасный degraded mode без записи в production.

## Данные и надежность

### Что нужно для продажи школе

- Надежная persist-модель в Supabase для всех сущностей.
- Миграции по порядку, без ручного “full setup” как единственного источника.
- Staging database.
- Backup/restore plan.
- Audit log.
- Soft delete для важных сущностей.
- Импорт учеников из CSV/XLSX.
- Экспорт оплат/учеников/расписания.
- Защита от дублей учеников по телефону.
- История изменений занятия.
- История действий сотрудника.

### Особо проверить

- Что будет, если два администратора одновременно меняют одно занятие.
- Что будет, если ученик записался, а администратор в этот момент удаляет время.
- Что будет, если инструктор отменяет занятие, а ученик смотрит кабинет.
- Что будет, если школа поменяла филиал/инструктора ученика.
- Что будет, если у ученика долг и запись запрещена.
- Что будет, если у ученика нет медсправки/договора, а школа включила запрет.

## Рекомендуемый порядок работ

### Этап 1 — стабилизация за 1-2 дня

- Починить typecheck.
- Починить mojibake.
- Обновить smoke под текущую продуктовую логику.
- Добавить typecheck + smoke в CI.
- Убрать прямой доступ к старой гостевой записи.
- Проверить live после деплоя.

Цель: чтобы проект перестал “случайно быть зеленым”.

### Этап 2 — безопасность и данные за 3-7 дней

- Supabase Auth для школы/сотрудников.
- RBAC и membership tables.
- RLS/RPC rewrite для admin actions.
- Убрать staff password как основной механизм.
- Перевести admin reads/writes с localStorage bridge на Supabase.
- Сделать audit identity.

Цель: можно давать реальной школе, не краснея за доступы и данные.

### Этап 3 — product launch flow за 2-4 дня

- Мастер подключения школы.
- Чеклист готовности.
- Empty states с точным действием.
- Импорт/ручное добавление учеников.
- Первое расписание сериями.
- Проверка публичной ссылки/кабинета ученика.

Цель: новая школа сама или с менеджером за 30-60 минут доходит до рабочего состояния.

### Этап 4 — кабинет школы как рабочий пульт за 3-5 дней

- Финальный UX audit всех разделов admin mobile/desktop.
- Убрать старые admin pages или спрятать их из сборки.
- Единый словарь продукта.
- Таблицы, фильтры, модалки, длинные значения.
- Платежи до MVP-уровня.
- Экспорт.

Цель: директор 40+ понимает день, деньги, проблемы и следующее действие.

### Этап 5 — запуск и контроль за 1-2 дня

- Production checklist.
- Staging/prod env.
- Security headers.
- Monitoring.
- Backup/restore.
- Legal docs review.
- Smoke после деплоя.

Цель: можно подключать первую платную школу и спокойно смотреть, как она пользуется.

## Итог

Самое важное: **не надо сейчас снова начинать с визуала**. Визуал нужно дополировать, но настоящий запуск упирается в фундамент:

- auth,
- данные,
- CI,
- тесты,
- юридическая аккуратность,
- онбординг школы,
- консистентность терминов и сценариев.

Если идти по правильному порядку, vroom можно довести до продаваемого MVP. Но если сейчас просто дальше шлифовать цвета и карточки, проект будет выглядеть лучше, а риски для реальной школы останутся теми же.
