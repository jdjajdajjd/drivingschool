# Vroom Full UI Audit

Дата: 2026-05-12
Домен проверки: https://vroom.today
Исключено из аудита: личный кабинет ученика `/student` и его внутренние экраны.
Проверено: публичная главная, публичная страница школы, поток записи, вход/регистрация, админка автошколы, кабинет инструктора, входы персонала и супер-админа.

## 1. Методика

Проверка была сделана в два слоя:

1. Визуальный ручной проход через браузер: смотрел цельность продукта, иерархию, плотность, читаемость, ощущение "рабочего пульта".
2. Автоматический обход Playwright: 20 маршрутов в 3 размерах экрана: desktop 1440x950, tablet 768x1024, mobile 390x844.

Сырые артефакты проверки:

- raw JSON: `C:\Users\First\AppData\Local\Temp\vroom-audit-1778615378650\audit-raw.json`
- скриншоты: `C:\Users\First\AppData\Local\Temp\vroom-audit-1778615378650`

Автопроверка показала:

- 60 проверенных комбинаций маршрута и viewport.
- 0 HTTP-ошибок.
- 0 найденных `undefined`, `NaN`, битых символов в видимом тексте.
- 0 горизонтального overflow в проверенных размерах.
- 0 консольных ошибок на проверенных маршрутах.
- 50 случаев мелких интерактивных элементов ниже комфортного стандарта 44 px, чаще всего 40 px кнопки, 36-41 px табы и поля с маленькой внутренней областью.
- На странице настроек найдено 11 полей без надежной программной связки label/id/aria в каждом проверенном viewport.

## 2. Главный вывод

Проблема сейчас не в том, что сайт "сломанный". Он в основном открывается, не падает и не расползается. Проблема глубже: Vroom ощущается как набор разных продуктов, собранных в один домен.

Сейчас одновременно живут как минимум пять визуальных языков:

1. Landing: светлый SaaS, синий акцент, крупные маркетинговые блоки.
2. Public school: бежево-черная карточная мобильная витрина.
3. Booking flow: бежево-черный booking-интерфейс с крупными карточками.
4. Admin: темно-teal операционный пульт.
5. Instructor/staff/superadmin: серо-синие служебные экраны.

Из-за этого пользователь не чувствует, что это одна система. Даже если отдельный экран сам по себе неплохой, переход между экранами дает ощущение "вышел в другой продукт".

Главная задача следующего этапа: не "покрасить красиво", а собрать единую дизайн-систему Vroom и прогнать через нее все поверхности, кроме личного кабинета ученика.

## 3. P0: что я бы исправил до нормального запуска

### P0.1. Единая визуальная система

Что видно:

- Landing держится на синем `#2442D8`.
- Public/booking живут в бежевом фоне, черных CTA и больших мягких карточках.
- Admin после последней правки ушел в petrol/teal.
- Instructor живет в синем `#1F3A8A`.
- Staff login использует яркий синий и другой стиль карточки.

Почему это плохо:

- Для директора автошколы это не "единый сервис за 5000 рублей", а набор разных интерфейсов.
- Поддерживать это будет тяжело: любое новое изменение будет усиливать хаос.
- У пользователя нет стабильной памяти: где primary, где secondary, где warning, где success.

Как исправить:

- Ввести один набор продуктовых токенов:
  - фон приложения;
  - фон рабочих поверхностей;
  - primary action;
  - secondary action;
  - danger/warning/success/info;
  - радиусы;
  - тени;
  - размеры кнопок;
  - размеры табов;
  - типографика H1/H2/card title/body/meta.
- Выбрать один primary для продукта. Я бы не оставлял одновременно синий, черный и teal как равноправные primary.
- Для Vroom как "рабочего пульта" я бы выбрал:
  - основной рабочий акцент: petrol/teal для админки и статусов управления;
  - черный только для brand/logo и сильных контрастных CTA в публичной записи;
  - синий убрать из staff/instructor или оставить только для информационных состояний.
- Свести все `bg-[#...]`, `text-[#...]`, `rounded-[...]`, `shadow-[...]` к компонентам и токенам. Сейчас в `src` найдено 1000+ прямых utility-значений, это главный источник неоднородности.

### P0.2. Админка: привести все страницы к одному "пульту"

Что видно:

- `/virazh-office-73q` уже выглядит как пульт: крупный hero, деньги, проблемы, быстрые действия.
- `/students` выглядит как таблица CRM.
- `/schedule` выглядит как календарь/таблица с множеством одинаковых окон.
- `/settings` выглядит как обычная форма настроек.
- `/documents`, `/exams`, `/reports`, `/users` визуально гораздо проще и слабее главной.

Почему это плохо:

- Главная задает ожидание дорогого продукта, а следующие страницы выглядят дешевле.
- Директору приходится каждый раз заново понимать структуру экрана.
- Нужные значения не всегда выделяются одинаково: долги, документы, неявки, просрочки, свободные окна.

Как исправить:

- Сделать единый admin page template:
  - верхняя строка: заголовок, короткое объяснение, один главный CTA;
  - ниже: 2-4 KPI/сигнала только если они помогают действовать;
  - дальше: рабочая зона с фильтрами и списком/таблицей;
  - справа на desktop: "что требует внимания" или "следующие действия";
  - на mobile: один поток, без мелких таблиц.
- Для всех admin pages ввести одинаковые компоненты:
  - `AdminPageHeader`;
  - `AdminToolbar`;
  - `AdminKpiCard`;
  - `AdminDataCard`;
  - `AdminStatusPill`;
  - `AdminActionButton`;
  - `AdminEmptyState`;
  - `AdminMobileList`.
- Убрать разные локальные реализации карточек, кнопок и фильтров.

### P0.3. Админская навигация на mobile

Что видно:

- Нижняя навигация показывает только 5 пунктов: Сегодня, Расписание, Ученики, Оплаты, Отчеты.
- Остальные важные разделы доступны через burger: Инструкторы, Машины, Филиалы, Документы, Экзамены, Настройки, Пользователи.
- Topbar на mobile занят логотипом, названием, logout и burger; это нормально, но "Выйти" стоит в зоне постоянного случайного нажатия.

Почему это плохо:

- Для директора 40+ часть системы кажется спрятанной.
- "Машины", "Филиалы", "Документы", "Экзамены" операционно важны, но не видны.
- Logout в верхнем углу слишком заметен по цвету и находится рядом с ежедневными действиями.

Как исправить:

- Нижнюю навигацию оставить только для 4-5 самых частых действий.
- Пятый пункт сделать "Еще", открывающий нормальную action sheet/меню.
- Logout убрать из постоянной красной кнопки в меню профиля/настройки.
- В topbar вместо красного logout оставить спокойный avatar/initials или меню.
- Для важных скрытых разделов на главной сделать "операционные плитки": Документы, Машины, Экзамены, Филиалы.

### P0.4. Страница "Ученики"

Что видно:

- Desktop: плотная таблица, хорошо сканируется, но выглядит сухо и местами как временная CRM.
- Mobile: карточки уже лучше, но в карточках много одинаковых серых/зеленых блоков, а главный смысл ученика теряется.
- Тестовые имена вроде `asdfafasf`, `hdhdhd hdhdusu` портят ощущение продукта. Даже если это демо-данные, визуально они ломают доверие.
- Телефоны не отформатированы: `79832858351`, `79027538685`.
- Статусы "нет", "готово", "Новая заявка" выглядят слишком одинаково по важности.

Почему это плохо:

- Это один из главных экранов продукта. Он должен быть предельно понятным: кто ученик, что с деньгами, документами, практикой и что делать.
- Сейчас много сигналов есть, но они не собраны в историю ученика.

Как исправить:

- Desktop:
  - оставить таблицу, но сделать ее "операционной": имя + этап + проблема в первом столбце;
  - телефон форматировать как `+7 ...`;
  - "Открыть" заменить на явную строковую affordance: вся строка кликабельна + маленькая кнопка `Карточка`;
  - статусы сделать ролями: долг красный/зеленый, документы amber/green, практика blue/gray.
- Mobile:
  - сделать верх карточки: имя, телефон, этап;
  - второй ряд: деньги, документы, ближайшее занятие;
  - третий ряд: назначенный инструктор + действие.
- Добавить быстрые фильтры по смыслу:
  - `Новые`;
  - `Долг`;
  - `Нет документов`;
  - `Без инструктора`;
  - `К экзамену`;
  - `Неактивные`.
- В демо/seed-данных заменить мусорные имена на реалистичные.

### P0.5. Расписание

Что видно:

- Desktop/week view показывает много одинаковых окон, но слабая визуальная иерархия.
- Mobile выглядит чисто, но неделя занимает много вертикального места.
- Кнопки переключения "День/Неделя", назад/вперед, "Сегодня" и "Создать окна" стоят рядом, но не образуют понятную панель управления.
- Свободные окна и занятые окна визуально конкурируют.

Почему это плохо:

- Расписание это сердце продукта. Админ должен за 5 секунд понять: что сегодня, где свободно, где конфликт, кого надо перенести.
- Сейчас интерфейс больше похож на календарный вид, чем на рабочий диспетчерский экран.

Как исправить:

- На desktop сделать два режима:
  - "День": основной рабочий список по времени, с группировкой по инструктору/филиалу.
  - "Неделя": обзор загрузки, не попытка показать каждое окно как равнозначную карточку.
- Добавить фильтры в sticky toolbar:
  - инструктор;
  - филиал;
  - категория;
  - статус: свободно/занято/прошло/отменено/проблема.
- Для свободных окон сделать менее громкое оформление, а занятия с учеником и проблемы выделять сильнее.
- На mobile:
  - сначала показывать выбранный день и список событий;
  - недельные карточки сделать компактнее;
  - кнопку `Создать окна` закрепить как главный CTA, но не ломать поток.

### P0.6. Настройки

Что видно:

- Mobile settings выглядит как длинная форма без явного разделения задач.
- Save находится сверху справа, но когда пользователь прокрутил вниз, непонятно, сохранены ли изменения.
- Часть полей/checkbox плохо связаны с label с точки зрения доступности.
- Разделы "Правила записи", "Финансы", "Уведомления", "Документы" смешиваются.

Почему это плохо:

- Настройки редко используют каждый день, но ошибка в настройках ломает бизнес-процесс.
- Админ должен понимать последствия каждого переключателя.

Как исправить:

- Разбить на вкладки/секции:
  - Профиль школы;
  - Запись;
  - Ограничения;
  - Уведомления;
  - Документы;
  - Оплаты;
  - Опасная зона.
- Добавить sticky save bar снизу/сверху: `Есть несохраненные изменения` + `Сохранить`.
- Checkbox-строки сделать 48-56 px и кликабельными всей строкой.
- Для сложных правил добавить короткое пояснение под полем: например, "за сколько часов ученик еще может отменить занятие".
- Деструктивные действия вынести в отдельную красную "Опасную зону", а не держать рядом с обычными настройками.

## 4. P1: важные улучшения после выравнивания основы

### P1.1. Public school page

Что видно:

- Страница визуально приятная, но слишком карточная и пустая на desktop.
- Главный CTA `Записаться на занятие` находится справа, а главный блок школы слева; на mobile CTA уезжает ниже первого экрана.
- Категории B/C/D занимают много места, но не дают полезного контекста.
- Разделы "Запись", "О нас", "Контакты" выглядят как табы, но по сути это разные части лендинга школы.

Как исправить:

- Первый экран публичной страницы должен отвечать на 3 вопроса:
  - что за школа;
  - где находится;
  - как записаться.
- На mobile главный CTA должен быть виден в первом экране или стать sticky bottom action.
- Категории превратить в компактные chips рядом с описанием.
- Добавить реальные рабочие сигналы:
  - ближайшие свободные дни;
  - количество доступных инструкторов;
  - филиалы;
  - телефон.
- Убрать ощущение "карточка рядом с карточкой"; сделать более уверенную композицию.

### P1.2. Booking flow

Что видно:

- Форма записи выглядит лучше многих остальных экранов, но есть слабые места:
  - нет явного H1 в DOM по автопроверке;
  - на mobile сетка слотов в две колонки делает карточки узкими;
  - disabled/занятый слот слишком похож на доступный, просто бледнее;
  - дата-карусель на mobile уходит вправо, это ожидаемо, но не хватает подсказки/градиента/scroll affordance;
  - выбранный слот и следующий шаг не ощущаются достаточно очевидно.

Как исправить:

- Сделать wizard-stepper:
  - 1. Дата и время;
  - 2. Данные ученика;
  - 3. Подтверждение.
- На mobile использовать один столбец слотов или крупные строки, а не две узкие карточки.
- Disabled слот подписывать причиной: `занято`, `недоступно`, `нет мест`.
- После выбора слота показывать sticky confirmation bar: время, инструктор, филиал, кнопка `Продолжить`.
- Добавить H1 технически и визуально корректно.
- Добавить фильтр по филиалу/инструктору прямо в шаге выбора, если у школы это включено.

### P1.3. Landing

Что видно:

- Landing самый "SaaS" из всех поверхностей: синий, крупный hero, маркетинговая подача.
- Он выглядит аккуратно, но слабо связан с админкой и публичной страницей автошколы.
- Оффер хороший, но можно сделать ближе к "рабочему пульту автошколы", а не к абстрактному SaaS.

Как исправить:

- Подтянуть визуальный язык к продукту: меньше маркетинговой синевы, больше реального интерфейса.
- Первый экран должен показывать не просто обещание, а мини-фрагмент операционного пульта: сегодня, долги, окна, проблемы.
- CTA оставить один главный: `Открыть демо`.
- Вторичный CTA: `Посмотреть запись ученика`.
- Три шага лучше описать бизнес-процессом автошколы: школа настроила, ученик записался, директор увидел операционку.

### P1.4. Staff login / Superadmin login

Что видно:

- Staff login и superadmin login выглядят как отдельная синяя auth-система.
- Кнопка `Войти без пароля` слишком сильная и потенциально сбивает с толку. Для демо это удобно, но для продукта выглядит небезопасно.
- На mobile карточка нормальная, но визуально не связана с Vroom admin shell.

Как исправить:

- Для демо-режима переименовать:
  - `Войти без пароля` -> `Открыть демо-доступ`;
  - `Войти по логину` оставить вторым.
- Для production убрать или спрятать демо-доступ по окружению.
- Привести фон, карточку, logo block и кнопки к тем же токенам, что admin.
- Добавить подпись "Демо-режим" только там, где это правда.

### P1.5. Кабинет инструктора

Что видно:

- Это не личный кабинет ученика, поэтому включено в аудит.
- Экран функциональный и понятный, но живет в другом стиле: серый фон, синий акцент, другие радиусы и другие карточки.
- Mobile выглядит аккуратно, но не как часть Vroom admin/public системы.

Как исправить:

- Привести к общим токенам Vroom.
- Оставить мобильный рабочий формат, но сделать карточку инструктора ближе к admin-паттернам.
- Кнопки `День`, `Дальше`, `Архив` поднять до 44 px.
- Empty state сделать более операционным: что сейчас, почему пусто, что делать администратору/инструктору.

## 5. P2: техническая и продуктовая чистка

### P2.1. В репозитории есть параллельные старые реализации

Что видно по коду:

- Есть текущие страницы `Today.tsx`, `Schedule.tsx`, `Students.tsx`, `Payments.tsx`.
- Параллельно лежат старые/альтернативные реализации:
  - `src/pages/admin/Dashboard.tsx`;
  - `src/pages/admin/Slots.tsx`;
  - `src/pages/admin/Bookings.tsx`;
  - `src/pages/admin/today/TodayPage.tsx`;
  - `src/pages/admin/schedule/SchedulePage.tsx`;
  - `src/pages/admin/people/PeoplePage.tsx`;
  - `src/pages/admin/money/MoneyPage.tsx`;
  - `src/components/layout/AdminSidebar.tsx`;
  - `src/components/layout/AdminBottomNav.tsx`.

Почему это плохо:

- Следующий агент или разработчик легко начнет править не тот экран.
- Это усиливает неоднородность: разные поколения интерфейса живут рядом.
- Typecheck уже падает на части старого кода, например `admin/people`.

Как исправить:

- Составить карту реально используемых маршрутов из `App.tsx`.
- Все неиспользуемые реализации либо удалить, либо перенести в `archive/` вне сборки, либо явно пометить как deprecated.
- После этого привести typecheck к зеленому состоянию.

### P2.2. Favicon и production headers

Что видно:

- В `index.html` указан `/favicon.svg`.
- HEAD-запрос к `https://vroom.today/favicon.svg` вернул `text/html`, то есть favicon фактически отдается как SPA fallback, а не как иконка.
- Для HTML нет HSTS/CSP headers.
- JS asset `index-rkrdPa6_.js` около 624 KB до gzip, Vite предупреждает о большом chunk.

Как исправить:

- Добавить реальный `public/favicon.svg` или заменить ссылку на существующий png/svg.
- Настроить Cloudflare headers:
  - `Strict-Transport-Security`;
  - базовый `Content-Security-Policy`;
  - `X-Content-Type-Options: nosniff`;
  - `Referrer-Policy`.
- Сделать code splitting:
  - отдельно admin;
  - отдельно public booking;
  - отдельно student cabinet;
  - отдельно superadmin.

### P2.3. Документация дизайна частично битая

Что видно:

- `VROOM_UI_STANDARD.md` в текущем виде содержит битую кириллицу при чтении из проекта.
- Это не ломает сайт, но ломает будущую работу: агент/разработчик может прочитать неверный стандарт или проигнорировать его.

Как исправить:

- Пересохранить документ в UTF-8.
- Сократить стандарт до реально исполняемых правил.
- Вынести tokens/components отдельно.

## 6. Экран за экраном

Сильные стороны:

Рекомендация:

### Admin Students

Сильные стороны:

- На desktop таблица плотная и сканируемая.

Проблемы:

## 8. Definition of Done

Перед следующим деплоем после редизайна:

- `npm run build` проходит.
- `npm run typecheck` проходит или все остаточные ошибки явно задокументированы.
- Проверены desktop 1440, tablet 768, mobile 390.
- Нет горизонтального overflow.
- Нет битого текста, `undefined`, `NaN`.
- Нет интерактивных элементов ниже 44 px для ключевых действий.
- На каждом рабочем экране есть один главный CTA.
- На каждом empty state есть объяснение и следующий шаг.
- Bottom nav не перекрывает важный контент.
- Public, admin, instructor, staff login ощущаются как один продукт.

## 9. Короткий вердикт

Сейчас Vroom уже можно открыть и использовать в базовом сценарии, но по ощущению это еще не цельный продукт за 5000 рублей в месяц. Главная проблема не в отдельных пикселях, а в отсутствии единой системы интерфейса. Если сначала выровнять tokens, компоненты, навигацию и смысловую иерархию, следующие правки станут намного быстрее и чище.

Я бы не начинал с точечного "поправь карточку тут". Я бы начал с системного прохода: один визуальный язык, один admin template, один набор статусов, один принцип CTA. После этого уже полировать конкретные экраны.
