## 1. Текущий контекст

vroom — React + TypeScript + Vite + Tailwind проект для автошкол.

В проекте есть:

- ученический кабинет;
- публичная страница школы;
- flow записи на занятие;
- админка автошколы;
- суперадминка;
- демо-кабинет инструктора;
- Supabase как будущий основной backend;
- localStorage как демо/cache/fallback слой.

Архитектура сейчас переходная:

- часть данных берётся из Supabase;
- часть данных хранится в localStorage;
- приложение сидит на демо-данных и fallback-логике;

- `/student` — ученический кабинет;

- `/school/:slug/book` — запись со страницы школы;
- `/booking/:bookingId` — подтверждение записи;
- `/virazh-office-73q` — админка школы;

## 3. Продуктовые принципы

### 3.1. Не усложнять работу автошколы

Любая новая функция должна отвечать на вопрос:

> создаёт ли это лишнюю работу админу или инструктору?

Если да — функцию не делаем или упрощаем.

### 3.2. Не требовать от инструктора подробных отчётов

Инструктор не будет после каждого занятия писать длинные комментарии.

Максимум, что можно просить:

- `Проведено`;
- `Ученик не пришёл`;
- `Отменено`;
- `Перенесено`;
- опционально выбрать тип занятия.

### 3.3. Ученик должен видеть следующее действие

Главная должна отвечать на вопрос:

> что мне сейчас делать?

Возможные состояния:

- нет записи — показать ближайшее окно;
- есть запись — показать следующее занятие;
- занятие сегодня — показать время, адрес и действия;
- есть незаполненные данные — показать, что нужно заполнить.

### 3.4. Не показывать данные, которых нет

Если данных нет, лучше показать:

- `Пока не назначено`;
- `Уточните в автошколе`;
- скрыть строку.

Нельзя показывать фейковые даты, группы и статусы.

### 3.5. Сначала реальность, потом красивые функции

Не делать сейчас:

- сложную карту навыков;
- AI-рекомендации;
- готовность к экзамену в процентах;
- автоматическое планирование тем занятия;
- лист ожидания;
- полноценный чат;
- платежи;
- фейковые акции;
- фейковые Госуслуги.
